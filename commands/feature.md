description: Add or change a feature in an existing codebase. Research, a plan you validate, a prototype you try, then the integration build.
argument-hint: "[the change you want]"
---

Superlite feature mode. Request: $ARGUMENTS

First, read `${CLAUDE_PLUGIN_ROOT}/assets/flows/feature.txt` (if the variable is not expanded, it is `assets/flows/feature.txt` in the superlite plugin directory) and print it verbatim in one ```text block, before anything else. It is stored, so never redraw or edit it. Skip it only when it was already printed this turn.

Design: `docs/feature-flow.md`. If the request is empty, ask for it in one line. Ask the orchestrator choice (human or AI) unless the user already said; run `sl orchestrator set human|ai`. Check `sl agent_specs status` (opt-in pre-impl specs; default off). When **on**, load `superlite:writing-specs`: a **spec** is what done looks like and why (durable); a **plan** is how (replaceable). Write `docs/plans/<date>-<topic>.spec.md` before or with the feature plan, and open it in the harness when status shows `open_in_harness: on` (`open_in_harness` covers the spec and the feature plan). Then six steps:

1. **Feature plan.** If the request is thin, ask for the feature in the user's words (at most one batched question, the `superlite:inventing` rule). Write `docs/plans/<date>-<topic>.feature.md` in the shape of `superlite:drafting` ("Feature plan"): goal and who it is for, what the user will see or do differently (screens, commands, endpoints or outputs, by target kind), `## Acceptance checks` a human can try. When agent_specs is on, acceptance checks must match the feature `.spec.md` (spec wins if they drift).
2. **Research the code.** Read before designing; research is read-only, as parallel Explore agents, one per area, each returning a short summary. Offer Graphify only if `sl graphify_gate` allows, and never install it without the user's yes. Add to the plan the `## Code map` (entry points and how the app is stood up, the files and tests the feature touches and their seams, the interfaces that must not change, the project's own conventions and toolchain; for a web UI, the repo's UI component set, or the fact that there is none), the prototype scope and an outline of the integration build.
3. **The human validates the plan.** Human mode: when `open_in_harness` is on (`sl agent_specs status`), open the plan for the user first (`superlite:drafting`, After writing). Then show the path and a five-line summary, ask in plain text "Reply approve to start, or tell me what to change", end your turn; after the reply, if you understand it as approval, run `sl orchestrator approve --review docs/plans/<date>-<topic>.feature.md`. Do not pass their words through. AI mode: open the `.feature.md` after research and do not wait; no approval; open choices become `Ruling:` lines.
4. **Prototype build.** `sl proto start --topic <topic> --run "<run command>" [--level L2]` cuts a worktree on `superlite/<topic>-proto`; the user's checkout is never touched. Load `superlite:feature-prototype` to cut the smallest container of the app (keep the entry point and what the feature touches, stub the rest; for a web UI, keep the repo's UI component set and compose the new screen from it, and use one-off markup only when the code map says there is no UI component set; L1 stubs by default, L2 only when the plan says real data shapes matter). Write a small agent-format plan in the worktree (`<worktree>/docs/plans/<date>-<topic>.proto.md`, at most 8 tasks, about a quarter of the integration estimate), its tests written against the acceptance checks, then `lint --stable` and `superlite:swarm` there. While it builds, draft the integration plan from the code map.
5. **The human tries it.** `sl proto tryout [--reach "<url, command or example calls>"] [--start]` prints how to run and reach the prototype and the acceptance checks; show it where the harness can (a preview pane for a web app). Human mode: ask the human, in plain text, to reply "it works" or list changes, end your turn; after the reply run `sl proto tryout --approve`. Changes go back to step 4 as a fix round (`sl proto start --topic <topic>` reopens it), not to a new plan unless they change the scope. AI mode: run the acceptance checks against the stood-up prototype and record the result with `sl proto tryout --approve --ruling "<result>"`. Until the try-out is approved, the integration build is blocked in human mode.
6. **Integration build.** First cut (or reopen) a **dedicated** integration worktree and branch for this feature only — never layer it onto another feature's checkout or a dirty `main`. Example: `git worktree add -b superlite/<topic> .superlite/worktrees/<topic> <base>` (base = the branch the user was on when the feature started), then move the agent root there. In that worktree, write the integration plan in the agent format with `**Review plan:** docs/plans/<date>-<topic>.feature.md`: one task per touched module, the existing interfaces FROZEN, migration tasks where data changes, seam checks between new and existing code, and the prototype's acceptance tests as the target. Code is ported from the prototype task by task, never merged: its stubs and fakes stay behind. Every existing test must still pass. Then the normal review, final review, tiered fixes and finish; the report shows the prototype and the integration as two parts. At finish run `sl proto discard` (`--keep-branch` if the user asks to keep it), move the agent root back to the main checkout, and remove the integration worktree the way `superlite:shipping` says. The flow does not leave a worktree it created. A keep that still has uncommitted work stays.

Scope rule for this mode: change only what the request needs. One feature per worktree (see AGENTS.md).

**Agent specs (optional).** `sl agent_specs on|off|status|open on|off|prefer on|off` (`open` covers plans and specs). When on, implementers write from the feature spec (and may add a task-local note under `.superlite/specs/<plan-topic>/` before TDD); report the spec path in DONE. When off, behavior is unchanged.
