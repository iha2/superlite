# superlite 0.3.1: post-benchmark fixes

Source: combined benchmark rep set `v` (2026-10-18). Across 3 reps superlite averaged 25.1 min against superpowers' 33.6, at the same cost. In reps 2 and 3 the parallel build ended at about 13 min, and another 10-18 min went on reviews, fixes and wrap-up. Rep 1 skipped the 0.3 flow entirely. Goal: cut the post-build tail and the pre-build wait, and stop the coordinator from doing work. User decisions are marked **(user)**.

**Status (2026-10-18, repo 950bd9a):** F1-F18 are built and committed; F19-F24 were added after the repo moved on (hooks, routing evidence, benchmark tooling, agent views, and two open items). F numbers never change: an item that was overtaken carries a **Superseded** note and stays. ## F1. The coordinator never fixes code (user)
The coordinator does not edit source or tests, and does not run raw `pytest`. Every fix goes to a fix-only agent. Routing depends on how well the fix is understood:

| Tier | Agent | Use when |
|---|---|---|
| 1 (**superseded by F18: `fixer-haiku` removed**) | `superlite:fixer-haiku` (haiku, effort high) | Fully specified: exact `file:line` and the change are known, e.g. a reviewer's concrete fix line, a missing import, CRLF, a rename. |
| 2 | `superlite:fixer-sonnet` (sonnet, effort medium) | Cause known; fix confined to one module, plus a regression test. |
| 3 | `superlite:fixer-sonnet-high` (sonnet, effort high; built as its own agent file because effort can't vary per call) | Cause known, but the fix spans modules or a seam, or it's a known probe class (deep recursion, huge input, protocol edge). |
| 4 | `superlite:fixer-opus` (opus, effort high) | Cause unknown and needs diagnosis, or a lower tier failed 2 rounds. |

- **Current tiers (after F18):** 1 `fixer-sonnet` (this also takes the fully specified changes of the old tier 1), 2 `fixer-sonnet-high`, 3 `fixer-opus`. The table above is F1 as first written; `fixing.md` has the current one.
- **Escalation:** after 2 failed rounds at a tier, move up one tier. Log each failed round with `incident`.
- **Owner reuse:** if the task's own implementer is idle, within its reuse limits (≤3 tasks, ≤50 min idle, and for fix work ≤40k context, not the 80k that applies to new tasks) and its model matches the tier, send it a fix-only brief instead of starting a fresh fixer. Over 40k, start a fresh fixer (F8).
- **Package reviewers** still fix what they find (D13), but must close every finding, including ones sent later, and report a closed list.
- **The final reviewer** is findings-only (Read, Grep and Glob tools; it never fixes). It answers `Verdict: APPROVED` or `CHANGES_REQUESTED` plus `file:line - problem - fix - tier N` lines, at most 300 words. Its findings go to fixers, routed by that tier and split by file. This narrows D13 and drops the old "final reviewer fixes" path.
- **Fixer contract:** fix only the named findings; add one regression test per fix; run `sl run_tests --fast` on the touched files (in the background, wait only for its summary); `commit_task` by path; report a closed list. Never refactor. Never touch files outside the finding.
- The coordinator never passes `model` to an agent call (it overrides the agent file), and never dispatches an extra or ad-hoc reviewer. If a review is inadequate, log a `Ruling:`.

## F2. All test runs in the background (user)
Every test run is `sl run_tests ... --background` (or the skill's equivalent): the full suite, fix-round fast runs and UI runs. Each writes `.superlite/test-summary.json`. Reviewers read the summary from their packet, and red results become findings handled under F1. The only wait is a summary check right before the final commit. No foreground suite runs, and no suite run after the merge.

## F3. Dispatch as plan sections are approved (user) - superseded by F13
Superseded by F13: `lint --stable` replaces section-by-section approval as the main way to dispatch early. `**Status:** draft` stays as a manual hold.
Don't wait for the whole plan. As each section of the plan is approved, dispatch its tasks while the next section is discussed.
- **Plan format:** each task block may carry `**Status:** draft`. A task is dispatchable only if it's approved (no Status line, or `**Status:** approved`) and every task it depends on is approved too. `next_tasks` and `dispatch` skip draft tasks and their dependents. `plan_tools taskgraph` and lint accept partial plans: draft tasks may still have placeholders, approved ones may not.
- **Interface guard:** a section is approved only once its Produces/Consumes interfaces are frozen. If a later section changes an interface an earlier task already consumes, the earlier task gets a follow-up fix task, not a restart.
- Lint, schedule and stubs run per section.
- With a pre-approved run (as in the benchmark), approve section by section anyway: dispatch the first section as soon as it's written and linted.

## F4. Rolling review of the last package
Batched per-package review stays the default. But once a package is the last one still building, review each of its tasks as it commits, so the review overlaps the build and only the final task's review is left afterwards.

## F5. Review packet carries source excerpts
In rep 2 the packet-only final reviewer gave up after 16 s for lack of code, which set off an improvised extra review. `pt_review packet` should include, per finding candidate, a bounded excerpt of the code involved: the changed hunks of the hot-spot files (diff against the base, capped per file and in total; suggested caps 120 lines per file and 600 overall). Keep the 15k plan cap separate.

## F6. Steer builds into subagent-driven-development
In rep 1 superlite loaded only `writing-plans`, then dispatched `general-purpose` agents and never ran any tool. `using-superlite` and `writing-plans` must say that any build with 2 or more tasks runs through `superlite:subagent-driven-development`, which is loaded before writing the plan. `general-purpose` agents are never used for build or review work.

## F7. Per-task records for the predictor
`bench/harness.py` must write per-task records into the score JSON, so that `predict.py --refit` works. Join each implementer dispatch (task id from its description, e.g. `T4 ...`) to the plan's task features (Components, LOC owned, Tests fast/slow, Model), read from the plan file in the run dir (`docs/plans/*.md`). Each record has `task, components, loc, tests, model, actual_s`. Then `sl predict --refit bench/results/combo-superlite-v2.json ...` must find observations.

## F8. Fix notes: compaction in a file
Subagents can't compact themselves, so the working state of a fix lives in `.superlite/fixes/<id>.md` (`<id>` = `F-<Tn>-<n>`, given in the brief), not in a long session.
- **Note format:** at most 1,500 chars, heading `# <id> · tier N · round R · FIXED|NOT_FIXED`, then Goal, Where (file:line ranges), Changed (what and why), Tried and failed (attempt, failure, reason), Evidence, Next. Every fixer round rewrites it cumulatively, even when the fix succeeded.
- **Later rounds and escalations** start a fresh agent whose brief is only `$SL`, `Tn`, the finding id and "read the note first". No transcript or report is pasted in, and the fixer never repeats anything in Tried and failed. This keeps a round to roughly 10-20k context instead of a reused 60-100k session, and a different model shares no cache anyway.
- **Owner reuse for fixes is capped at 40k context** (see F1).
- `.superlite/` is never committed. A note still `NOT_FIXED` after the last tier becomes a `Ruling:` in the closing message.
- Built in: `agents/fixer-*.md`, `skills/subagent-driven-development/fixing.md` (commit d27db81).

## F9. Build-path rules in `writing-plans`
Aimed at the pre-build wait and the build's critical path.
- Consumers test only against stubs with small fakes, never the real producer. Integration tests that run both sides go in one small integration task per package at the end. This replaces "the integration test belongs to the later task".
- **`CHAIN:` lint:** fails when the predicted critical path is over 2.5 times the longest task and has 3 or more tasks. Fix by stubbing more interfaces, or add `Ruling: sequential - <why>`.
- **No Opus implementers (`OPUS-TASK:` lint):** `Model` is always `sonnet` (or `haiku` for F10); `Model: opus` is rejected, replacing the old "opus for Complexity 7+". A task that seems to need Opus is split, and the hard part goes to `fixer-opus`. Security-sensitive code still gets an Opus review.
- Built in: `skills/writing-plans/SKILL.md` and the lint in `plan_tools.py` (commit 7bad271).

## F10. `Kind: mechanical` tasks and `implementer-haiku`
A task field `**Kind:** design | mechanical` (default `design`).
- **Mechanical** means the what is fully decided: LOC owned ≤ 150, Components ≤ 2, `Tests: fast`, no Review Focus case in deep, numeric, state or protocol, and test code or named tests with exact inputs and outputs. Never: parsers, evaluators, servers, UI, anything with state or an ambiguous spec.
- **`KIND:` lint** rejects a mechanical task that breaks a rule, and `Model: haiku` on any non-mechanical task.
- SDD sends mechanical tasks to `superlite:implementer-haiku` (haiku, effort high, same READY protocol). It follows the task literally and stops at NEEDS_CONTEXT or BLOCKED rather than guess.
- **Misses** (NEEDS_CONTEXT, BLOCKED or red) go to tier 2 (`fixer-sonnet`; **after F18 this is tier 1**) with a fix note and are logged as `incident --kind assumption --context "kind-miss Tn"`, so the first-time pass rate can be measured. That rate is not measured yet.
- Built in: `agents/implementer-haiku.md`, `writing-plans`, `fixing.md` (commit eb3a032). The `KIND:` lint was uncommitted when this was written; it is committed since (5d73881).

## F11. Superlite-only benchmarks and the kill guard
- Benchmarks run superlite only (user, 2026-10-18). `bench/run_combo.sh` takes `ARMS` (which arms to run) and `REPS_PARALLEL` (reps in parallel).
- **Kill guard:** in rep v1 the superpowers arm ran `taskkill //F //IM python.exe` and killed both harness runners. The superpowers arm now gets superlite's `block-unsafe-kill` as a settings-level PreToolUse hook; it adds no skills or context (`bench/harness.py`, commit c10e53b).
- **New goal G2:** beat superlite's own 0.3 time (26.9 min, mean of v2 and v3) by about half, so about 13.4 min.
- Built in: commits 7bad271 and c10e53b.

## F12. One size band (benchmark w3)
- The 3-min split cap and the "mergeable" rule (variable context under 18k, or under 1 min) measured different things and overlapped: every w3 task was flagged one way or the other (actuals 101-445 s).
- The only measure is predicted time: `config/predictor.json` `size_band` (`low_min` 1.5, `high_min` 6.0). Over `high_min`, lint fails `SIZE:` (split). Under `low_min`, `NOTE:` (consider merging), never a failure. The 80k context ceiling stays.
- `predict --refit` moves the band: `high_min` is the 90th percentile of measured task times clamped to [4, 8]; `low_min` is 2.5 times the agent start overhead.
- Docs: `writing-plans` (Split by interface rule 3, lint list), `subagent-driven-development`. Spec D33.

## F13. Lint, extract what is stable, fix the rest
- `lint --stable` splits the plan into STABLE and FIX tasks with reasons and writes `.superlite/stable.json`. Stable means: own checks pass, every Consumes has a clean Produces line somewhere (even from an unstable task), no taskgraph edge to an unstable task, not on a flagged `CHAIN:`.
- SPEC coverage, `CHAIN:`, the size cap and `MISSED TARGET` are plan-level: they never block stable tasks.
- `dispatch` offers only stable tasks. The coordinator dispatches the stable set at once, patches only the FIX tasks (edits, never full rewrites), re-lints, and dispatches the newly stable ones.
- Stable and dispatched tasks have frozen interfaces. A later change is reported as `FROZEN:` and becomes a follow-up fix task.
- Replaces F3's section-by-section approval as the main early dispatch; `**Status:** draft` stays as an optional manual hold. Brainstorming now asks for one approval of the whole doc.
- Evidence: on w3's first-draft plan a prototype would have dispatched T2, T4 and T5 at 104 s instead of the actual 322 s; every stable task mapped to a SPEC section. Spec D34.

## F20. Routing evidence and what is applied (D41)

`bench/routing_evidence.py` writes `bench/results/routing-recommendation.{md,json}` from 45 task samples (10 Haiku, all on combo T8 `refs`). Measured (means, n = 3 each, all passing): Haiku 84.0 s, $0.0113, 12.3 tool calls against Sonnet 72.4 s, $0.118, 8.3; mini prime on Haiku 72.9 s to 64.0 s and $0.0110 to $0.0076. Recommended and not applied: LOC <= 100 as a rule, Haiku reuse limits of 3 tasks and 40k context (`routing.json` allows 6 and 60k), a 120 s slack rule. **The slack rule is superseded by the user's final decision:** a mechanical task on the critical path never goes to Haiku. Haiku misses go straight to a Sonnet fixer. Open: Haiku evidence is one task; no miss observed.

## F22. Short lines instead of file views; YAML dropped (D43)

The language-adapter design proposed a YAML converter. Measured on real input tokens: YAML is smaller than pretty JSON on 3 of 4 datasets (8 to 31%), 4% larger on the fourth, and 2 to 11% larger than compact JSON on all four. Done: nothing to build; there is no `to_yaml` and no `config/views.yaml`, and `test-cmd` is JSON. Agents keep reading short whitelisted lines (`DISPATCH NOW:`, `TIERS:`, `stats:`, `budget:`, dispatch lines).

## F23. OPEN: the router threshold (D44)
