# Grill step for the idea process

## Goal

Borrow the idea of `/grill-me` (aihero.dev/skills-grill-me): interview the user about an idea until the plan is firm. Keep superlite lean: the grill is **capped, stateless and folded into the plan**, never a second spec. It is for whoever reads the plan next, an AI or a human orchestrator, and for the user who answers it.

What we take from grill-me: ask in rounds (the whole frontier at once, never one question at a time), only ask what answers depend on, stop when nothing is left unstated, and stop grilling what only a prototype can answer.

What we do not take: open-ended length, a standalone slash command, a glossary or ADR files.

## What changes

- **When:** every mode that works on existing code, always **after discovery** and before anything is built or fixed:
  - Feature: step 2b, after research, before the human validates the plan (up to 2 rounds).
  - Debug: after the cause is found and reproduced, before the fix (1 round: what the correct behavior is, what must not change, how far the fix may reach).
  - Review: after the target and its diff are read, before reviewers fix (1 round: what the change is meant to do, what risk matters most, what is out of bounds).
  - Small: no grill. It stays inline; if it grows, it switches to feature and gets the grill there.
  - MVP and regular builds on an empty folder: unchanged (nothing to discover yet).
  Feature detail: The code map exists by then, so questions cite real files, seams and frozen interfaces ("export.py writes CSV in two places; change both or only the API path?") instead of guessing. Step 1 stays as is: at most one batched question, and only when the request is too thin to research.
- `skills/inventing/SKILL.md` gains a short **Grill** block holding the rules; `commands/feature.md`, `commands/debug.md` and `commands/review.md` each gain one line that runs it at their discovery point, on what was found:
  0. **Questions are chosen to cut cost.** Cost is tasks, files, tests, agents, prototype rounds, rewrites and the tier the work needs. Rank candidates by what the answer removes or cheapens and ask only those that change the plan's size, direction or tier. A good answer either shrinks the plan ("does this need to exist?", "reuse X instead of building Y?", "which parts can wait?") or makes it mechanical enough for a cheaper agent ("one pattern for all five call sites?", "copy X exactly?", "exact names and values?"), so more tasks can be `Kind: mechanical` for Haiku. The recommended option is the cheapest that still meets the goal. Everything else is decided silently as `Assumption:` or `Ruling:`.
  1. Never ask what the code map or request already answers; state the finding instead.
  2. Skip it when nothing material is open (the request and code map settle what, who, how it is checked and the seams).
  3. Round 1 is the whole frontier in one `AskUserQuestion`, at most 4 questions, recommended option first so "yes to all" is one click.
  4. Round 2 only for questions that depend on round 1 answers. Never a round 3.
  5. "I don't know" or "you decide" is an answer: record `Assumption:` and move on.
  6. A look-and-feel question is not grilled: record `Prototype decides:`; the try-out settles it.
  7. Human mode asks the user. AI mode grills itself: it writes the same round 1 frontier, answers each question from the code map, the request and the best-known default, then runs round 2 on whatever those answers open (same caps). Each answer is a `Ruling: <decision> (because <reason>)`, and the plan is **updated in place** (goal, what changes, acceptance checks, integration outline) so it reads as one plan, not as a plan plus a log. Nothing is asked and nothing waits.
- The result is not a file. It becomes a `## Decisions` section of at most 10 lines in the `.feature.md` (`Decided:`, `Assumption:`, `Prototype decides:`, `Ruling:`). Answers that change scope or the integration outline are folded into those sections, so the human approves one coherent plan in step 3.
- `skills/drafting/SKILL.md` "Feature plan" lists `## Decisions`; `docs/feature-flow.md` describes the new step and its caps.
- Not changed: `commands/small.md`, MVP and regular flows, `skills/using-superlite/SKILL.md` (1883 of 2000 characters), `assets/flows/*.txt`, the CLI, hooks, manifests.

## Acceptance checks

- Run `/superlite:feature` with a vague request ("make the export better"): after research you get one batch of at most 4 questions with a recommended answer each, at most one follow-up batch, then a plan with a `## Decisions` section of 10 lines or fewer. Total time to a plan: two answers, not a conversation.
- Run it with a precise request that names the file, the behaviour and the check: no questions are asked, the plan states the understanding.
- Every question asked has an answer that lowers cost: a smaller plan, or work specified tightly enough for a cheaper agent tier. A question whose answers all cost the same is not asked.
- Answer "I don't know" to a question: it shows up as `Assumption:` and is not asked again.
- Ask a look-and-feel question ("should it be a modal or a page?"): it lands as `Prototype decides:` and is not asked.
- Run `/superlite:debug` on a bug whose expected behavior is unclear: after the cause is found you get one batch, no second round, then the fix.
- Run `/superlite:review` on a branch: after the diff is read you get at most one batch before reviewers start.
- AI mode: no `AskUserQuestion` is made; the AI answers its own round 1 and round 2 questions, the plan holds `Ruling:` lines (10 or fewer), and the sections they affect are edited to match.
- No new files are written by the grill itself, and `skills/using-superlite/SKILL.md` stays at or under 2000 characters.
- `pytest tests/scripts` passes.

## Code map

- Entry points: `commands/feature.md`, `commands/mvp.md` (flow prompts); `skills/inventing/SKILL.md` step 2 holds the shared ask rule that feature mode cites ("the `superlite:inventing` rule"); `skills/drafting/SKILL.md` line ~149 defines the feature plan shape; `docs/feature-flow.md` step 1 is the design record.
- Tests that pin docs and flows: `tests/scripts/test_feature_flow.py`, `test_doc_contract.py`, `test_flows.py`. Read them before editing wording they may assert.
- Interfaces that must not change: the `AskUserQuestion` single-batch rule in `inventing` (up to 4 questions, orchestrator choice in the same call), `superlite-cli orchestrator set/approve --review <feature.md>`, the `.feature.md` headings `superlite-cli proto tryout` reads (`## Acceptance checks`), `skills/using-superlite/SKILL.md` size cap, `assets/flows/*.txt` verbatim.
- Conventions: skill text is terse, imperative, one rule per sentence; keep LF endings; harness manifests list skills by name, and no new skill is added, so none need edits.
- Toolchain: `python -m pytest tests/scripts`; wording lint via the doc-contract tests. Not a web UI, so no UI component set.

## Decisions

- Decided: the rules live in a section of `inventing`, not a new skill or command, because AGENTS.md says keep it lean and inventing is where "ask once" already lives.
- Decided: caps are 2 rounds and 4 questions per round (the `AskUserQuestion` limit); bounded work gets 1 round.
- Decided: stateless, no file, 10 lines of `## Decisions` in the plan.
- Decided: feature, debug and review, always after discovery so questions use what was found (your call, 2026-11-02). Debug and review get one round only. Small, MVP and regular are unchanged.
- Decided: in AI mode the grill is self-directed and edits the plan in place; rulings are listed in the closing message as `inventing` already requires.
